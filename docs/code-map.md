- Background work: `apps/web/src/inngest/functions.ts` for the generate-card registration and step boundaries with its pure helpers in `generation-helpers.ts`, `apps/web/src/inngest/source-fetching.ts` for Direct Exa, StableEnrich, budgets, and source-gate orchestration, `apps/web/src/inngest/contact-enrichment.ts` for async people/email enrichment and cited person reads, `apps/web/src/inngest/card-enrichment.ts` for the async post-first-usable block-enrichment worker (`block-enrichment-patch.ts` holds the extraction-to-patch mapping shared with `functions.ts` so the two paths cannot drift; the worker also files the card's `expandedDescription` and owns the contact dispatch, so every basics ending routes through it whenever the stored card lacks a description, and its failures emit `enrichment.failed`, never `generation.failed`, onto the parent run's trail), `apps/web/src/inngest/research-section-generation.ts` for section generation plus the section-job step path, `apps/web/src/inngest/worker-env.ts` for provider env subsets and worker flags, and `apps/web/src/inngest/card-storage.ts` for storage compatibility guards. The two background enrichment functions take optional per-function concurrency caps from `INNGEST_CARD_ENRICHMENT_CONCURRENCY` and `INNGEST_CONTACT_ENRICHMENT_CONCURRENCY` (unset = no cap) so they cannot starve user-facing generation in the shared Inngest account pool. Since 2026-07-22 the analysis path runs synthesis and verification as their own memoized steps (`synthesize-card`, `verify-synthesis`) after `generate-card`, emitting the additive progress events `synthesis.started`, `verify.started`, and `verify.complete` (with `metadata.claimCount`); a verify retry replays the memoized synthesis draft instead of re-paying the synthesis call. `ANALYSIS_SOURCE_REFRESH` (`full` | `targeted` | `skip-fresh`, default `full`) gates the analysis-mode stableenrich re-fetch on the reuse branch in `source-fetching.ts`; runs stamp their mode into the trace (`providers.stableenrich.analysisSourceRefresh`) and the `source.found` event metadata so modes are distinguishable from traces alone. Since 2026-08-12 two more memoized steps run between `synthesize-card` and `verify-synthesis`: `fetch-founder-voice` and `emphasis-read`, both driven by `apps/web/src/inngest/emphasis-read.ts` (step bodies, `fv`-prefixed citation windowing, and the post-verify prune that caps cross-run citation accumulation) over the `packages/providers/src/founder-voice/` lanes. They gate on `EMPHASIS_READ_ENABLED` (default on) and a thin-file check that runs in code before either step, so a thin card pays for neither the lane fetch nor the `emphasis_read` LLM stage; a semantic emphasis failure degrades to `nothing_notable` rather than failing the run. Progress events `emphasis.started` and `emphasis.complete` bracket the pair. Since 2026-08-25 the how-it-wins read no longer runs inside the analysis path at all: the emphasis pair runs alone again, and once the analysis run stores fresh synthesis it records `how-it-wins.started`, writes `trace.howItWins = { enabled, status: "deferred" }`, and admits a durable job in step `admit-how-it-wins-v2` (`requestHowItWinsJob` in `apps/web/src/inngest/how-it-wins-jobs.ts`) before dispatching it in step `request-how-it-wins-v2` to the separate `how-it-wins-read` Inngest function in `apps/web/src/inngest/how-it-wins-function.ts`, which requires `executionContractVersion: 2` on the event and rejects anything else before touching the database. Admission failure records `how-it-wins.complete` with `status: "failed"` and a `reasonCode` itself, in step `persist-how-it-wins-admission-failure`, because no job row means no background function will ever close the trail. On the happy path the job's handler, `howItWinsV2Handler` in `how-it-wins-v2.ts`, runs the judge, frozen writer, and verifier as resumable stages, gated by `HOW_IT_WINS_ENABLED` and the same thin-file check; every terminal path, including the ten-minute reconcile cron and the status route settling an expiry, closes the trail once through `recordHowItWinsJobOutcome` in `how-it-wins-jobs.ts`, recording `how-it-wins.complete` on the parent run's trail (with `metadata.status` and `reasonCode`) whatever the outcome. The analysis run itself never waits on any of it, and this event is what the shipped extension waits for before it stops showing a reading state.

## Extension manifests and Firefox

- Extension manifests and browser builds: `manifest.config.ts` takes a `browser` parameter. The Chrome branch must keep its exact key order (the dist manifest is diffed for byte stability). The Firefox branch swaps `side_panel` for `sidebar_action`, declares `background.scripts` in source (CRXJS's firefox target crashes on a service_worker-only source manifest), and carries the gecko ID `cold-start@semitechie.vc` plus `gecko.update_url` → `https://cold-start.semitechie.vc/firefox/updates.json` (self-hosted updates; unlisted AMO builds get no update hosting; `scripts/firefox-release.mjs` stamps `apps/web/public/firefox/updates.json` from a signed XPI). - Firefox identity: `browser_specific_settings.gecko.id` makes `runtime.id` (and therefore the `x-cold-start-extension-id` header) the stable `cold-start@semitechie.vc`, while the Firefox `Origin` header is a per-install random UUID (Bugzilla 1405971) and must never be used as identity. ## LLM provider routing and the provider matrix

## Generation data flow

Data flow: `/api/generate` runs the user-facing profile jobs (`basics`, `analysis`) in-process in the route invocation by default: it creates the run row, starts `generateCardHandler` through the inline step executor in `apps/web/src/inngest/inline-dispatch.ts`, and keeps the invocation alive past the 202 with `after` (route `maxDuration` 300s), so the first progress event never waits on Inngest's dispatcher. `GENERATION_DISPATCH=inngest` flips profile runs back to queue dispatch on the next deployment; section jobs and the enrichment workers always dispatch through Inngest. Either way the route streams generation status events back to the caller (the contract version is pinned in `packages/core/api-contract.json`; read that file for the current value rather than trusting any literal here); the extension and web progress feeds render those events. A `running` row whose event trail goes silent for over 5 minutes (a recycled instance mid-inline-run) is retired by the watchdog in the POST route (`deadGenerationRunTarget` in `packages/db`), letting the next request start fresh. `apps/web/src/inngest/functions.ts` owns the generate-card handler, its retry boundaries, and trace merging; the handler runs against either step executor via the narrowed `GenerationStepTools` in `client.ts`; its pure run helpers live in `generation-helpers.ts`, and the section-job path runs through `runResearchSectionJobStep` in `research-section-generation.ts`. Inngest event names and step ids are frozen through refactors: durable-execution identity depends on them. Source fetching, contact enrichment, async card enrichment, storage guards, worker env helpers, and provider trace helpers live in neighboring `apps/web/src/inngest/*` modules. The `basics` path returns a first-usable card fast; remaining block enrichment happens afterward in the async card-enrichment worker. Full card assembly stays in `packages/pipeline/src/generate-card.ts`, which receives injected provider and LLM functions. DB callers import through `packages/db/src/index.ts`, which re-exports the focused repository modules under `packages/db/src/repositories/`. Public card routes strip synthesis. Extension card routes return synthesis only after `apps/web/src/lib/extension-auth.ts` accepts the request.

## How it wins job tables

- `sources.published_at` (migration `packages/db/drizzle/0020_source_published_at.sql`) stores the publish date a provider returned, written by `recordSource` through `recordSourcesForCard` and read back by `findSourcesBySlug`; `providerSourcesFromStoredSources` falls back to `sourcePublishedAt` for rows stored before the column. The ledger (`buildEvidenceLedger`) and `withSourcePageDetails` carry it onto citations, and `howItWinsEvidencePacketFromCard` gives it to the judge as `sourceDate`.
- `how_it_wins_jobs` (migration `packages/db/drizzle/0019_how_it_wins_jobs.sql`) holds durable job state for the background How it wins read: root budget accounting (one manual retry shares the root cap), short-lived private candidate and checkpoint storage, and SQL functions for admission (`admit_how_it_wins_job`), manual retry admission (`admit_how_it_wins_retry`), lease (`claim_how_it_wins_job`), finish (`finish_how_it_wins_job`), expiry (`expire_how_it_wins_job`), and the card write (`complete_how_it_wins_job_with_card`). Repositories: `packages/db/src/repositories/how-it-wins-jobs.ts` (admission, reads, dispatch, the lease claim, lifecycle) and `how-it-wins-job-state.ts` (call reservation and settlement, stage checkpoints, recovery payloads), both over the internal row module `how-it-wins-job-rows.ts`, which the package index never re-exports; the assertion and SQL-shape helpers they share with `alpha.ts` live once in `packages/db/src/validation.ts`. Job rows are pruned 90 days after their last update by the retention cron route and `alpha:prune` (`packages/db/src/alpha-retention.ts`, `scripts/alpha-prune.ts`), the same fixed-age window as `how_it_wins_judgments`.

## Friend alpha system

- Friend alpha system: `packages/db/src/repositories/alpha.ts` (migrations 0009-0014 and 0016) for invites, presentation capabilities, installations, source-scoped attempt quotas, allowances, and run-request reserve/settle; `apps/web/src/lib/extension-auth.ts`'s `authenticateExtensionRequest` for the DB-backed `AlphaPrincipal` it returns (an `alpha` principal carries `inviteId`, `installationId`, and per-invite `scopes`; the `operator` principal matched against `EXTENSION_API_TOKEN` is the transitional all-scopes bypass that predates per-invite auth); `apps/web/src/app/alpha/` and `apps/web/src/app/api/alpha/invite/*` for the invite page and its invite inspect/redeem/status routes; `apps/web/src/app/api/alpha/events/route.ts` and `packages/core/src/alpha-analytics.ts` for the analytics event contract, mirrored by the extension's queuing client in `apps/extension/src/shared/alpha-analytics.ts`; `apps/web/src/app/api/alpha/retention/route.ts` for the cron-driven 30-day event and handled-access-request prune; `scripts/alpha-invite.ts`, `alpha-reissue-link.ts`, `alpha-revoke.ts`, `alpha-prune.ts`, `alpha-delete-tester.ts`, and `alpha-status.ts` for operator scripts.

## Generation cost telemetry

- Generation cost telemetry: `packages/core/src/generation-trace.ts` defines the trace shape, `packages/pipeline/src/cost.ts` tallies per-run Anthropic spend. Use both together when debugging cost regressions. Total run cost is five streams: `costUsdAnthropic` (all LLM spend, any provider), `costUsdAgentcash` (StableEnrich wallet delta), `providers.directExa.estimatedCostUsd` (Direct Exa bills the Exa account at ~$0.007/search), `providers.websets.estimatedCostUsd` (Websets credits, ~15/email-enriched item; rate tunable via EXA_WEBSETS_CREDIT_USD), and `trace.emphasis.estimatedLaneCostUsd` (the founder-voice lanes' xAI and Exa-web spend, budgeted under $0.10/run, zero when the emphasis read is thin-filed, disabled, or a lane fails). The Exa-billed fields are tracked since June 2026; older traces report nothing.
